Agenten

Werkzeuge standardisiert anbinden (MCP)

Das Model Context Protocol ist ein gemeinsamer Stecker zwischen KI-Assistenten und den Systemen, die sie nutzen sollen.

Das Problem: jede Anbindung einzeln

Ohne gemeinsame Regeln braucht jeder Assistent für jedes System einen eigenen Anschluss.

Ein Agent wird erst nützlich, wenn er an Systeme kommt: Kalender, Dateien, Ticketsystem, Datenbank. Jede Anbindung muss jemand bauen. Ohne gemeinsame Regeln heißt das: Jeder Assistent braucht für jedes System einen eigenen Anschluss.

Bei zehn Assistenten und zwanzig Systemen sind das bis zu 200 Einzelanbindungen. Jede muss gebaut, getestet und gepflegt werden.

Beispiel aus dem Alltag

Wer weltweit reist, kennt das Problem mit den Steckdosen. Jedes Land hat einen anderen Stecker, und du brauchst einen Adapter für jedes Land. Mit einem gemeinsamen Stecker bräuchtest du nur einen.

Die Idee: ein gemeinsamer Stecker

Wer ein System anbietet, baut einmal einen Anschluss. Jeder Assistent mit dem Standard nutzt ihn.

Das Model Context Protocol, kurz MCP, legt fest, wie ein Assistent ein System nach seinen Fähigkeiten fragt und wie er sie aufruft. Es wurde ursprünglich von Anthropic vorgestellt und ist ein offener Standard, den inzwischen viele Anbieter unterstützen.

Wer ein System anbietet, baut einmal einen Anschluss nach diesem Standard. Jeder Assistent, der den Standard spricht, kann ihn nutzen. Aus „jeder mit jedem“ wird „jeder mit dem Standard“.

Server und Client

Der Client fragt den Server, was er kann, und ruft seine Werkzeuge im Auftrag des Modells auf.

Zwei Rollen sind wichtig:

  • Der MCP-Server steht vor einem System und macht dessen Fähigkeiten bekannt, zum Beispiel „Termine lesen“ oder „Ticket anlegen“. Der Name täuscht: Es ist oft ein kleines Programm, das auf deinem eigenen Rechner läuft.
  • Der Client ist die Anwendung, in der der Assistent läuft. Er fragt die angeschlossenen Server, was sie können, stellt das dem Modell als Werkzeuge zur Verfügung und führt Aufrufe aus.
Beispiel aus dem Alltag

Ein Reisebüro vermittelt dir Hotels, Flüge und Mietwagen. Das Büro ist der Client, die Anbieter sind die Server. Du sagst dem Büro, was du willst, und es spricht mit jedem Anbieter in dessen Sprache. Der Standard macht diese Sprache einheitlich.

Was ein Server beschreibt

Ein Server bietet Werkzeuge, Ressourcen und Vorlagen an. Für Agenten zählen die Werkzeuge.

Ein Server bietet vor allem drei Dinge an: Werkzeuge, die etwas tun, Ressourcen, also Daten zum Lesen, und Vorlagen für wiederkehrende Aufgaben. Für Agenten sind die Werkzeuge am wichtigsten.

Jedes Werkzeug hat genau die Angaben, die du von der Seite Was ist ein Agent? kennst: einen Namen, eine Beschreibung und die Parameter mit ihren Typen. Der Client liest diese Liste, das Modell wählt anhand der Beschreibungen, der Client ruft den Server auf und reicht das Ergebnis zurück.

Ein Beispiel mit einem erfundenen Kalender-Server: Er meldet das Werkzeug termine_lesen mit der Beschreibung „Liefert die Termine für ein Datum“ und dem Parameter „datum“ (Text, Pflicht). Fragst du den Assistenten „Was steht morgen an?“, rechnet er das Datum aus, ruft das Werkzeug auf und fasst die Termine zusammen. Der Assistent musste den Kalender dafür nicht kennen, nur den Standard.

Ein Server kann auf deinem eigenen Rechner laufen oder im Netz erreichbar sein. Je weiter weg er läuft, desto wichtiger werden Anmeldung und verschlüsselte Verbindung. Die Einzelheiten des Protokolls brauchst du für das Verständnis nicht.

Merke

MCP ändert nichts an der Schleife des Agenten. Es standardisiert nur, wie Werkzeuge beschrieben und aufgerufen werden.

Sicherheit: wem vertraust du?

Ein Server ist Code mit Zugriff auf deine Systeme. Prüfe ihn wie jede Software.

Ein MCP-Server ist Programmcode, der Zugriff auf deine Systeme bekommen kann. Das verlangt dieselbe Sorgfalt wie jede andere Software. Frage vor dem Anschließen:

  • Wer hat den Server gebaut, und ist die Quelle vertrauenswürdig und gepflegt?
  • Welche Rechte bekommt er? Gilt das Prinzip der geringsten Rechte, siehe Rechte und Freigaben?
  • Wo liegen die Zugangsdaten, und wer kann sie lesen?
  • Welche Aktionen verlangen eine Freigabe durch einen Menschen?
Beispiel aus dem Alltag

Eine Steckdosenleiste vom Discounter ohne Prüfzeichen steckst du auch nicht blind hinter dein teuerstes Gerät. Ein neuer Stecker macht die Verbindung einfach, aber nicht automatisch sicher.

Auch Beschreibungen sind Text

Beschreibungen und Ergebnisse landen im Kontext. Behandle sie wie fremden Text.

Die Beschreibung eines Werkzeugs landet im Kontext des Modells. Ein böswilliger oder fehlerhafter Server kann dort Anweisungen unterbringen, und Ergebnisse von Werkzeugen können Prompt-Injection enthalten. Behandle darum alles, was von einem Server kommt, wie fremden Text. Das gilt auch dann, wenn die Verbindung selbst technisch geschützt ist.

Nutzen und Grenzen

MCP macht ein Werkzeug erreichbar, nicht besser und nicht sicherer.

Der Nutzen ist groß, wenn viele Systeme angebunden werden: Anschlüsse lassen sich wiederverwenden, und du bist nicht an einen Assistenten gebunden. Eigene Server für eigene Systeme sind meist klein.

Die Grenzen sind schnell genannt. MCP macht ein Werkzeug nicht besser, es macht es nur erreichbar. Viele Werkzeuge gleichzeitig verwirren Modelle, besonders kleine, und füllen den Kontext mit Beschreibungen. Auch die Qualität einer Beschreibung bestimmt, ob das Modell richtig wählt. Und die Sicherheit bleibt deine Aufgabe.

Beispiel aus dem Alltag

Ein Werkzeugkasten mit genormten Aufsätzen: Jeder Aufsatz passt auf jeden Griff, auch von einem anderen Hersteller. Ob der Aufsatz scharf ist und ob du ihn für die Schraube brauchst, sagt die Norm dir nicht.

Einordnung

MCP ist ein Anschluss, kein Agent. Die Schleife bleibt dieselbe.

MCP ist ein Anschluss, kein Agent. Das Agent-Labor nutzt seine Werkzeuge fest eingebaut. Ginge es nach dem Standard, stünden hinter rechne, uhrzeit und dokumentsuche je ein Server, und das Modell würde dieselbe Schleife durchlaufen.

Ob du MCP brauchst, hängt von deinem Fall ab. Für einen Agenten mit zwei eigenen Funktionen reicht oft ein direkter Aufruf. Für eine Landschaft mit vielen Systemen und wechselnden Assistenten spart der Standard viel Arbeit.

Das nimmst du mit

  • MCP ist ein offener Standard: Systeme melden ihre Werkzeuge einheitlich, Assistenten nutzen sie einheitlich.
  • Ein Server beschreibt Werkzeuge mit Name, Beschreibung und Parametern. Der Client reicht sie dem Modell und führt Aufrufe aus.
  • Der Standard macht Anbindung leicht, aber nicht sicher: Prüfe Quelle, Rechte und Freigaben jedes Servers.

Teste dich

  1. Welches Problem löst MCP vor allem?
    Antwort

    Es ersetzt die Einzelanbindung jedes Assistenten an jedes System durch einen gemeinsamen Standard. Der Standard verringert die Zahl der Einzelanbindungen. Er ist der gemeinsame Stecker.

  2. Was macht ein MCP-Server?
    Antwort

    Er macht Fähigkeiten eines Systems als Werkzeuge, Daten oder Vorlagen bekannt. Der Server steht vor einem System und beschreibt, was man damit tun kann.

  3. Was gehört zur Beschreibung eines Werkzeugs?
    Antwort

    Name, Beschreibung und Parameter. Das Modell wählt anhand dieser Angaben. Klare Beschreibungen verbessern die Wahl.

  4. Warum solltest du einem neuen MCP-Server nicht blind vertrauen?
    Antwort

    Weil er Code mit Zugriff auf deine Systeme ist und auch Beschreibungen und Ergebnisse manipulierte Anweisungen enthalten können. Ein Server hat Rechte und liefert Text in den Kontext des Modells. Prüfe Quelle und Rechte, und behandle seine Ausgaben als fremden Text.

  5. Was gilt für MCP und die Qualität eines Werkzeugs?
    Antwort

    MCP macht ein Werkzeug erreichbar, nicht besser. Zuverlässigkeit, gute Beschreibung und passende Rechte bleiben deine Aufgabe.
